# Braftonium plugin — developer & AI guide

This is the **Braftonium plugin** (`braftonium-new`): a **shared, client-agnostic** WordPress
plugin that ships reusable Gutenberg blocks, block patterns, standard microstyles, an editor
add-on, and admin settings, used across **many** client sites.

This `CLAUDE.md` is the **standalone source of truth for working ON the plugin** — adding/changing
blocks, patterns, microstyles, settings, and the build. It is self-contained: you don't need any
other repo's docs to work here.

> **Two different relationships with this plugin — don't confuse them:**
> - **Consuming a site build** (the usual case): the plugin is **READ-ONLY**. You only *use* its
>   blocks/patterns/settings. Never edit anything here. (Enforced by the website repo's guardrails.)
> - **Working ON the plugin** (this guide): you're explicitly updating Braftonium. Everything below
>   applies. The cardinal rule still holds: **everything you add must be GENERIC and
>   client-agnostic** — no client names, no project-specific copy/colours/media/classes. Client- or
>   site-specific work belongs in the theme or a `{client}-custom-components` plugin, never here.

## Build system — one command

```bash
npm run build      # from the plugin root: installs children, then builds EVERYTHING:
                   #   blocks child  → sass (legacy block CSS) + wp-scripts (React blocks src→build)
                   #   gutenberg-addon → wp-scripts
npm run watch                          # watch legacy block SCSS
npm run start --prefix blocks          # wp-scripts watch for React blocks (src/)
```

How it's wired (root `package.json` is a **pure orchestrator** — no deps of its own):
- `build` → `install:all` (installs the `blocks` + `gutenberg-addon` children with `--no-save`) →
  `compile` → `build:blocks` (`npm run build --prefix blocks`) + `build:addon`.
- `blocks/package.json` `build` = `sass-compile` (enumerated legacy block dirs) + `build:react`
  (`wp-scripts build`).

**Build gotchas (learned the hard way — keep them):**
- The blocks sass script compiles **explicit block dirs** (`banner:banner …`), never `sass .` —
  npm auto-creates a recursive `braftonium` symlink in `blocks/node_modules`, and `sass .` would
  follow it into an infinite loop and hang. Add new LEGACY block dirs to both sass scripts.
- Child installs use `npm install --no-save` so npm doesn't keep re-adding that `file:..` symlink
  dependency to the child `package.json`.
- **Artifacts:** compiled `*.css` is git-ignored and regenerated by the build; block `build/*.js`
  is committed (matches the legacy blocks). The one hand-authored CSS that IS committed is
  `general-settings/standard-microstyles.css` (via a `.gitignore` `!` exception).
- Prereq: Node + npm on the host (the WP container has no npm). Run `npm run build` before
  packaging (`bin/package-plugin.sh`).

## Blocks

Two kinds coexist. **Always check `blocks/<slug>/render.php`'s `AI / REUSE FRONTAGE` docblock** for
how an existing block is meant to be used (every block carries one — see below).

1. **Legacy pre-bundled** (`blocks/<slug>/`): banner, cta, custom-row, custom-list,
   custom-list-item, slide, slider. Committed `build/index.js`, no in-repo source. **Don't try to
   rebuild these** — leave them as-is.
2. **Modern React** (`blocks/src/<slug>/` → `blocks/build/<slug>/`): the way to build NEW blocks.

### How to add a new React block (the `nav-dropdown` recipe)

1. **Scaffold** `blocks/src/<slug>/` with the standard `@wordpress/create-block` file set:
   - `block.json` — `apiVersion:3`, name `braftonium/<slug>`, `"category":"braftonium"`,
     `"textdomain":"braftonium"`, attributes, supports, and the file refs:
     `"editorScript":"file:./index.js"`, `"editorStyle":"file:./index.css"`,
     `"style":"file:./style-index.css"`, `"render":"file:./render.php"`.
   - `index.js` — `registerBlockType(metadata.name, { edit, save })`; `import './style.scss'`.
   - `edit.js` — the React editor UI (`import './editor.scss'`).
   - `save.js` — for a dynamic block: `return <InnerBlocks.Content />` (render.php builds the rest).
   - `render.php` — server render (dynamic block). **Must open with the frontage docblock.**
   - `style.scss` (front + editor) and `editor.scss` (editor-only).
2. **Make it self-contained & generic:** bundle the block's own behaviour/layout CSS in
   `style.scss` (don't rely on a theme's classes). Use generic class names `braftonium-<slug>__*`.
   Reference `--wp--preset--*` tokens with neutral fallbacks; never hardcode a client's colours.
3. **Build:** `npm run build` (root) — wp-scripts compiles to `blocks/build/<slug>/` and copies
   `block.json` + `render.php`. **No PHP registration change needed:** `blocks/blocks.php`
   auto-registers every `blocks/build/*/block.json` (and the legacy `blocks/<slug>/`).
4. **If the block is a child of another block** (e.g. a `core/navigation` item), core's parent has a
   fixed allowed-blocks list — append yours server-side in `blocks/blocks.php`:
   ```php
   add_filter( 'register_block_type_args', function ( $args, $name ) {
       if ( 'core/navigation' === $name && ! empty( $args['allowed_blocks'] ) ) {
           $args['allowed_blocks'][] = 'braftonium/<slug>';
       }
       return $args;
   }, 10, 2 );
   ```
5. **Editor parity caveat:** a block's `editorStyle` (`editor.scss` → `index.css`) loads in the
   **post editor** but NOT the **Site Editor canvas iframe**. If the block is used inside a template
   PART, mirror its editor-only rules in the consuming theme's `editor-style.scss`.

### ⭐ Block frontage — REQUIRED on every block

Every block's `render.php` opens with an `AI / REUSE FRONTAGE` docblock (same convention as
patterns; ignored by WordPress, read by AI/devs). Keep it in sync with the block's attributes and
markup. Tags:

```php
/**
 * Render: braftonium/<slug>
 * @var array $attributes  @var string $content  @var WP_Block $block
 *
 * ───────────────────────────────────────────────────────────────────────────
 * AI / REUSE FRONTAGE — block usage metadata, NOT parsed by WordPress.
 * @intent       <what the block is for, one line>
 * @options      <every attribute / editor control + enum values + defaults>
 * @innerblocks  <allowedBlocks / template / orientation>   (or @parent for a child block)
 * @render       <output wrapper + key classNames>
 * @classes      <the classNames it outputs, for SCSS targeting>
 * @microstyles  <which microstyles apply, e.g. braftonium-bg-full / braftonium-bg-wrap>
 * @usewhen      <when to reach for it>   @avoidwhen <when not to>
 * @responsive   <breakpoint behaviour>   @editor-note <authoring caveats, if any>
 * ───────────────────────────────────────────────────────────────────────────
 */
```

## Patterns

Patterns are registered **like a block theme** (no `register_block_pattern()` calls). The loader
`general-settings/block-patterns.php` scans `patterns/*.php`, reads each file's header docblock via
`get_file_data()`, and registers it on `init` (gated on the `patterns` feature flag). It also scans
a consuming theme's `braftonium/patterns/*.php`.

To add one: copy `patterns/_template.php` → `patterns/<slug>.php`. **Title + Slug are required**
(files without them, and files prefixed `_`, are skipped). Recognised headers mirror core theme
patterns: `Title`, `Slug`, `Description`, `Viewport Width`, `Inserter`, `Categories`, `Keywords`,
`Block Types`, `Post Types`. The file's OUTPUT is the pattern content (PHP runs first, e.g.
`content_url()`). Base categories: `braftonium`, `braftonium-sections`, `braftonium-containers`,
`braftonium-components` (any other referenced category is auto-registered).

### ⭐ Pattern frontage — REQUIRED on every pattern file

After the recognised headers, every pattern carries an `AI / REUSE FRONTAGE` docblock (the `@`-tag
lines are ignored by WordPress but describe the layout for reuse). Keep it in sync with the markup.

```php
<?php
/**
 * Title:          Two Column (Text + Image)
 * Slug:           braftonium/two-column
 * Categories:     braftonium, braftonium-sections
 * Description:    A basic two-column layout.
 *
 * ───────────────────────────────────────────────────────────────
 * AI / REUSE FRONTAGE — NOT parsed by WordPress.
 * @intent       <what this layout is FOR, one line>
 * @layout       <band/grid structure + responsive>
 * @composition  <the blocks it's built from>
 * @classes      <stable CSS classes>      @microstyles <braftonium-* used>   @blockstyles <is-style-* used>
 * @slots        <what to replace when reusing>
 * @reusewhen    <when to reach for this>  @avoidwhen <when not to>
 * @responsive   <stacking behaviour>
 * ───────────────────────────────────────────────────────────────
 */
?>
<!-- wp:... -->
```

**Authoring rules:** pure generic markup, generic class names (a reusable layout concept or a
microstyle/block-style — never the content/topic), tokens via `var(--wp--preset--*)`, portable URLs
(`content_url()` / relative links). No client specifics — Braftonium patterns are plug-and-play.

## MicroStyles

Three layers (canonical class prefix is **`braftonium-*`**):

1. **Standard microstyles (the cross-project utility set).** Registered + enqueued by
   `general-settings/standard-microstyles.php`; CSS in `general-settings/standard-microstyles.css`
   (enqueued on `enqueue_block_assets` → front end + editor iframe). Set:
   - Universal: `braftonium-mt-0`, `braftonium-mb-0`, `braftonium-full-bleed` (100vw breakout;
     inner gutter derived from `var(--wp--style--global--content-size)` — no hardcoded breakpoint),
     `braftonium-overlay-dark`, `braftonium-col-span-2`/`-3`/`-4`, `braftonium-pt-half`/`-pb-half`
     (grouped-section seam padding; value from `--braftonium-section-padding-half`, with fallback).
   - Text: `braftonium-eyebrow`, `braftonium-uppercase`, `braftonium-tracking-tight`,
     `braftonium-tracking-wide`, `braftonium-measure`.
   - Legacy `ms-*` aliases are kept on the same rules for back-compat; new work uses `braftonium-*`.
   - **Add one:** add the picker entry in `standard-microstyles.php` (universal vs text-scoped) AND
     the `.braftonium-<name>` CSS in `standard-microstyles.css`. Keep values generic (tokens/vars).
2. **Container background microstyles** (`blocks/blocks.php`): `braftonium-bg-full` (background spans
   the viewport) / `braftonium-bg-wrap` (background constrained to content width), offered on
   banner, cta, custom-row, custom-list, slider.
3. **Admin-managed microstyles** (per-site, not code): the **Braftonium › General Settings ›
   MicroStyles** table — see settings schema below.

All three feed the **"Braftonium MicroStyles"** multi-select in every block's **Advanced** panel via
the `braftonium_class_list` filter; selecting one writes the class into the block's
`braftoniumClasses` attribute + `className` (wired by `gutenberg-addon/src/index.js`).

## Settings — frontage / schema (how to use each)

Admin UI lives under the **Braftonium** menu. When *consuming* a site you generally **respect**
these (an admin sets them); when *working on the plugin* you maintain them in `general-settings/`.
`general-settings/settings.php` is the canonical source for exact sub-keys.

### Feature flags — `general-settings/features.php`
- **@option** `braftonium_general_settings['features']` · **@read** `braftonium_feature_enabled($key)`
  (unknown/unset ⇒ **true**).
- **@keys** `blocks`, `patterns`, `inject_scripts`, `custom_posts`, `dev_tools`.
- **@use** Gate features. The main plugin file only loads each module when its flag is enabled, so a
  consuming site may have blocks/patterns/CPTs turned OFF — don't assume they're available.

### General settings — `general-settings/settings.php`
- **@option** `braftonium_general_settings` (single option, array). Keys:
  - `debug_on` (bool) — admin-only PHP error display.
  - `admin_override` (email) — forces `admin_email`/`new_admin_email`.
  - `google_api_key` (string) — used only by the legacy ACF map block.
  - `fallback_image_id` (int attachment id) — featured image for posts that lack one (front-end
    render only). **@use** respect it; don't hardcode a fallback elsewhere.
  - `revisions_enabled` (bool, default ON) — revisions for posts/pages/CPTs.
  - `features` (see above) and `microstyles` (see below).

### Admin-managed MicroStyles — `general-settings/settings.php`
- **@option** `braftonium_general_settings['microstyles']` — array of
  `{ label, value (class), block_types[] (empty = all), css (declarations only), enabled (bool) }`.
- **@editor** exposed via the `braftonium_class_list` filter; CSS injected on front end + editor.
- **@security** saving raw `css` requires `unfiltered_html`.
- **@use** site-specific class options an admin adds — distinct from the code-shipped standard
  microstyles. Don't duplicate a managed microstyle's CSS in code.

### Custom post types — `general-settings/custom-posts.php`
- **@option** `braftonium_custom_post_types_new` (`[{post_type_title, post_type_options:[tax]}]`),
  `braftonium_custom_post_types_taxonomies` (`[{name, slug}]`); registered on `init`
  (`create_custom_post_types`). Rewrite-flush flag: `braftonium_custom_posts_needs_flush`.
- **@filters** `braftonium_modify_custom_post_type($args,$title)`, `braftonium_taxonomy_filter($args)`.
- **@use** read these options (or query registered types) to discover a site's content types.

### Scripts & Styles injector — `general-settings/inject-scripts-styles.php`
- **@option** `braftonium_injector` (global rules) · **@meta** `_braftonium_injector` (per-post).
- **@shape** `{ location (header|body_start|body_end|footer), inject_method (inline_js|inline_css|
  enqueue), load_strategy (normal|async|defer), script_id, html_value, url_value, html_disable }`.
- **@use** the sanctioned place for site/page-level script-or-style injection (NOT a `core/html`
  block or inline `<style>`/`<script>` in content). Inline rules require `unfiltered_html`.

### Dev tools — `general-settings/dev-tools.php`
- **@option** `braftonium_dev_tools['debug_on']`. Debug-log viewer (tails `WP_DEBUG_LOG` /
  `wp-content/debug.log`).

### Helper functions — `general-settings/useful-functions.php` (always loaded)
- `consoleJS($txt)` (echo a `console.log` script), `readingTime($postId,$makeMinutes,$appendTxt)`
  (~200 wpm), `includeForAdmin($file)` (include only for `manage_options`).

## Editor add-on — `gutenberg-addon/`

A React bundle (built by its own wp-scripts) enqueued on `enqueue_block_editor_assets`. It:
- adds a `braftoniumClasses` (array) attribute to every block except `gravityforms/form`;
- renders the **"Braftonium MicroStyles"** multi-select in each block's Advanced panel; and
- registers the REST route **`/{plugin}/v{version}/braftonium-class-list`** (POST `{blockType}` →
  `[{label,value}]`), built in `class-loader.php`, whose options come from the `braftonium_class_list`
  filter (all three microstyle layers).
Build it via the root `npm run build` (`build:addon`).

## Conventions (recap)

- **Generic & client-agnostic only.** No client names/copy/colours/media/classes anywhere here.
- **Namespacing:** blocks `braftonium/<slug>`, classes `braftonium-<slug>__*` / `braftonium-*`,
  textdomain `braftonium`, category `braftonium`.
- **Every block** opens `render.php` with the `AI / REUSE FRONTAGE` docblock; **every pattern** file
  carries the pattern frontage. Keep them in sync with the code.
- **PHP files** start with `if ( ! defined( 'ABSPATH' ) ) { exit; }`.
- **Verify before commit:** `php -l` changed PHP; `npm run build` succeeds and the block/pattern
  registers (in the editor inserter under "Braftonium"); confirm the front end and the editor match.
